# epoll 网络编程学习笔记（3 天）

> 从 `tcp_server.cpp`（阻塞单连接）出发，五个版本逐步演进。
> 每个版本只加一件事，加完就跑通、就 commit。

---

## 总览：五步演进

| 版本 | 加了什么 | 解决的问题 | 代价 |
|---|---|---|---|
| **v0** | 阻塞式，一次一个连接 | 基线，对照组 | 一个客户端占死一个线程 |
| **v1** | 非阻塞 + epoll **LT** 多连接 | 一个线程管 N 个连接 | `epoll_wait` 频繁唤醒 |
| **v2** | 切 **ET** + 循环读到底 | 减少唤醒次数 | 代码复杂度上升，必须读干净 |
| **v3** | 发送队列 + `EPOLLOUT` 按需订阅 + 水位 | 可靠发送 + 自我保护 | 多一层用户态缓冲 |
| **v4** | 一对多广播：遍历 map 转发 | 一份数据要发给多个客户端 | 遍历中清理的复杂度 |

**核心心法：每次只改一件事。改完能跑，再动下一件。**

## v0：阻塞式单连接

### 流程

```
socket → bind → listen → accept → recv → 打印 → 循环
```

阻塞模式下 `accept` / `recv` 都会把整个线程卡住，所以同时只能服务一个客户端。

### 踩的坑

| 错误 | 正确做法 |
|---|---|
| 用了中文引号 `”…”` | 全部改 ASCII 的 `"` |
| `std::end` | `std::endl`（end 是迭代器，endl 才是换行+刷新） |
| 缺 `<cstring>` | `memset` 需要它 |
| `cout << buffer` | `cout.write(buffer, bytes)`，否则遇到 `\0` 就停 |
| `listen(fd, 5)` | `listen(fd, SOMAXCONN)`，让内核用系统上限 |

### 认知纠正（这一条最重要）

当时对三个基础问题的回答全错，值得记下来：

1. ❌ "listen fd 和 client fd 类型不同" → **都是 `int`**，是内核 fd 表的**下标**。
2. ❌ "内核帮进程维护一个 fd 列表" → 内核只维护**每个 socket 对象**，fd 只是引用它的整数。
3. ❌ "epoll 的优势是为了线程池" → epoll 的优势是**一个线程能管 N 个连接**，跟线程池无关。

## v1：epoll LT + 多连接

### 加了什么

- 所有 fd 设 `O_NONBLOCK`
- `epoll_create1` / `epoll_ctl(ADD)` / `epoll_wait` 三步曲
- `std::unordered_map<int, Conn>` 登记所有连接
- listen fd 和 client fd **分开处理**

### LT 的特点

只要条件成立，**每一轮 `epoll_wait` 都会报告**。代码简单，但唤醒次数多。

### 踩的坑

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 开头写 `int epoll_ctl(...)` | 变成函数声明，调用没执行 | 去掉开头的 `int` |
| `epoll_wait(client_fd)` 只传 1 个参数 | 编译不过 | 四个参数：epfd, evs, maxevents, timeout |
| `close(client_fd)` 写在 `if` 外面 | **连接一接上就断** | 只在该关的地方关 |
| `fcntl(server_fd, ...)` 设非阻塞 | 设到了"门"上，不是新连接上 | 必须对 `client_fd` 设 |
| `else if (n == 0)` 用了 `epoll_wait` 的 `n` | 逻辑错乱 | 要用 `recv` 的返回值 `bytes` |

**第 3、4 条是同一类错误：搞错了作用对象。**
`server_fd` 是门，`client_fd` 是进来的人。门和人是两回事。

## v2：切换到 ET

### 三条铁律

1. **所有 fd 必须非阻塞**（否则循环读会永久卡死）
2. **`recv` 要循环读到 `EAGAIN`**
3. **`accept` 也要循环到 `EAGAIN`**

### 为什么必须读干净

ET 只在"状态从无到有"的那一瞬间通知一次。如果你只读了一半就回去等，
剩下的数据还在缓冲区里，但**不会再有新的边沿**，通知永远不来了 → 数据烂在缓冲区。

### LT 和 ET 的本质区别

| | LT | ET |
|---|---|---|
| 通知次数 | 条件成立就一直通知 | 只在变化时通知一次 |
| 代码复杂度 | 低 | 高（必须循环读干净） |
| 唤醒次数 | 多 | 少 |
| 适用场景 | 连接数不多、追求简单 | 高并发、追求性能 |

**Redis 用 LT 也没问题**——不是 ET 就更高级，是取舍不同。

### 踩的坑（这一段最密集）

| 错误 | 后果 | 正确做法 |
|---|---|---|
| `n == 0` 只 `erase`，不 `DEL`/`close` | **CPU 100% 死循环** | 三件套 `DEL → close → erase` |
| `EAGIN` 拼写错 | `errno` 判断失效 | `EAGAIN` |
| `errno == EAGAIN \| EWOULDBLOCK` | 位或，结果永远非 0 → 永远为真 | `\|\|` 逻辑或 |
| `while` 包住打印但没包住 `recv` | 无限刷屏 | `recv` 必须在循环体内 |
| EINTR 重试后 `insert(data, data+len)` | **数据重复发送** | `insert(data+n, data+len)`，从断点续 |
| EINTR 分支里漏掉重发的 `send` | 数据丢了 | 重试要真的再调一次 |
| `if (errno = EINTR)` | 赋值不是比较，永远为真 | `==` |
| 把 `n == 0` 当成功 | 漏掉对端 FIN | `recv == 0` 是对端关闭 |

### `recv` 的三态（必须背下来）

```cpp
int bytes = recv(fd, buffer, sizeof(buffer), 0);

if (bytes > 0)   { /* 收到数据 */ }
else if (bytes == 0) { /* 对端发了 FIN，该关了 */ }
else { /* bytes == -1，看 errno */
    EINTR      → 被信号打断，重试
    EAGAIN     → 数据读完了，正常退出循环（⚠ 连接还在！）
    其他        → 真出错，关闭
}
```

> **`errno` 只在失败时有意义。成功时它只是上一次的残留值。**

## v3：发送队列 + EPOLLOUT

### 加了什么

```cpp
struct Conn {
    int fd;
    std::vector<char> sendq;   // 待发送数据
    size_t sent = 0;           // 已搬进内核的偏移量（游标）
};
```

三个新函数/机制：

1. **`queue_send`** —— 先尝试 `send`，塞不进就追加到 `sendq`
2. **`flush_sendq`** —— `EPOLLOUT` 来了，把 `sendq` 剩下的继续塞进内核
3. **`EPOLLOUT` 按需订阅/退订** —— 有积压才挂，发完就摘

### 完整数据流

```
客户端
  ↓ 网络
【内核接收缓冲区】        ← 你摸不到
  ↓ recv()
【buffer[64KB]】         ← 你的栈内存（收的落点）
  ↓ queue_send()
【sendq】                ← 你的 vector（发的候车厅）
  ↓ send()
【内核发送缓冲区】        ← 你摸不到
  ↓ 网卡
客户端
```

**两条传送带，互不相通。** `buffer` 和 `sendq` 之间没有自动通路，
要发就得显式调一次 `queue_send` 拷过去。

### 踩的坑

| 错误 | 后果 |
|---|---|
| `map1.emplace(client_fd, int)` | 传了类型不是值 → `Conn{client_fd, {}}` |
| `printf("%d", wait_count)` | `long` 要用 `%ld` |
| `if (n == 1 && errno == EINTR)` | 少了负号，分支永远不成立 → `n == -1` |
| `fcntl(server_fd, F_SETFL, flag2 \| EPOLLOUT)` | **把 epoll 事件位当 fcntl 标志位**，会改坏 fd 的打开标志 |
| 重复定义 `int fd` | 同一作用域重定义，编译不过 |
| recv 循环里 `fcntl(server_fd, F_GETFL)` | 每轮查一次又不用，纯浪费 |
| **`MOD` 时写成 `EPOLLOUT \| EPOLLET`，漏了 `EPOLLIN`** | **积压期间收不到任何数据**（见下） |
| `queue_send` 返回值没检查 | 给已死的连接挂门铃 |
| 错误分支里用 `continue` | 回到 `while(1)` 对**已关闭的 fd** 继续 `recv` → 双重 close，可能关掉别人的连接 |

**最阴险的那条：`MOD` 是整体替换，不是追加。**

```cpp
// 错误：把 EPOLLIN 抹掉了，积压期间这个连接聋了
mev.events = EPOLLOUT | EPOLLET;

// 正确：在原有基础上加一位
mev.events = EPOLLIN | EPOLLET | EPOLLOUT;
```

在流媒体服务器里，这会导致"推流推到一半，客户端发来的暂停指令永远收不到"。

### C++ 语言坑：聚合体初始化

```cpp
struct Conn {
    int fd;
    std::vector<char> sendq;
    size_t sent = 0;   // ← 这一行让它不再是"聚合体"
};

Conn{client_fd, {}};   // C++11/14 编译不过
```

C++11/14 规定：带**成员默认初始化器（NSDMI）**的类型不是聚合体，
所以 `{a, b}` 会被当成构造调用。**C++17 才放宽这条。**

解法：`-std=c++17`（推荐），或给 `Conn` 加构造函数。

## 今天想了很久的两个点

### 一、`EPOLLIN` 和 `EPOLLOUT` 都是**手动订阅**

**曾经错误的模型**：以为 `OUT` 是内核挂上去的状态指示器，
"有 OUT = 内核告诉我可写"，"没 OUT = 内核告诉我满了"。

**正确的模型**：

> **`epoll_ctl` 是你的笔，`epoll_wait` 是内核的嘴。**
> 内核永远不会主动往你的注册表里加东西，它只报告你已经订阅的东西。

```
┌──────────────────┐         ┌──────────────────┐
│   epoll 注册表    │   ≠    │    内核池子       │
│  你通过 ctl 决定  │         │   客观状态        │
│  fd=5 → IN | ET  │         │  接收池空 发送池空 │
└──────────────────┘         └──────────────────┘
```

**"没挂 OUT" 只说明一件事：你没订阅。**
不代表内核满了，也不代表内核空了——它只代表**你不知道，也不关心**。

真值表：

| 注册表里有 OUT 吗 | 发送池实际状态 | 内核通知你吗 |
|---|---|---|
| 没有 | 满 | 不通知 |
| 没有 | 从满变空 | **不通知**（压根没订阅） |
| 有 | 满 | 不通知（还没空） |
| 有 | 当前空着 | 立刻报一次（`MOD` 会重新检查） |
| 有 | 从满变空 | **通知** |

**"挂 OUT" 到底是什么**：

> 向内核登记一句话：**"等发送池有空位了，叫我一声。"**

为什么必须登记？因为 `send` 刚返回了 `EAGAIN`，你有三条路：

| 做法 | 结果 |
|---|---|
| 死循环反复试 `send` | CPU 100% 空转 |
| 什么都不做 | 数据永远躺在 `sendq` 里 |
| **登记 OUT，然后走人** | 内核有空位时叫醒你 |

### 两者的生命周期**不对称**（这是整个写方向的核心）

| | `EPOLLIN` | `EPOLLOUT` |
|---|---|---|
| 什么时候订阅 | `accept` 时 `ADD` **一次** | 有积压时 `MOD` 加上 |
| 什么时候退订 | **永远不退** | 发完立刻 `MOD` 摘掉 |
| 为什么 | 就绪是**例外**，常挂不空转 | 就绪是**常态**，常挂会空转 |

**就绪概率对比**：

- `EPOLLIN`：大部分时间没数据 → 稀疏触发 → **挂着很安全**
- `EPOLLOUT`：发送缓冲区大部分时间是空的 → **每轮都触发** → 一直挂就是空转

**比喻**：

> `EPOLLIN` 是信箱的来信提示灯——有信才亮，一直开着没事。
> `EPOLLOUT` 是停车场的车位播报——场子基本一直有位，所以它一直在播。
> 你只有**车没处停**的时候才需要听它，停好了就该关掉。

### 完整闭环

```
① EPOLLOUT 提醒到了
   → flush_sendq 往内核塞
   → 塞完 → MOD 摘掉 OUT（退订）
   → 塞不完 → 不摘，继续等

② EPOLLIN 提醒到了
   → recv 读进 buffer
   → queue_send 往 sendq 放
   → 塞不进（sent < size）→ MOD 挂上 OUT（订阅）
   → 回到 epoll_wait 等

③ 下一轮 EPOLLOUT → 回到 ①
```

`①` 和 `②` 通过 `sendq` 这个中间站连起来，`OUT` 是它们之间唯一的信号线。

---

### 二、`sent < sendq.size()` 到底在比什么

**曾经错误的模型**：

- 以为 `sent` 是"我往队列里送了多少"
- 以为 `size()` 是"队列的最大容量"

**正确模型**：

```
sendq:  [====已搬进内核====|----还没搬走----]
        0                 sent              size()
                           └── size()-sent ──┘
```

- **`sent` 是游标**：从头开始，已经搬走多少字节
- **`size()` 是当前存量**：队列里现在一共多少字节（不是容量上限，vector 会自己扩容）
- **`size() - sent`**：还剩多少没搬走

所以：

> **`sent < size()` 等价于队列里还有剩，也就是该挂 OUT 了。**

**注意因果关系**：

- `sent < size()` 是**现象**（还有货没搬走）
- "内核发送缓冲区满了"是**原因**（上次 `send` 返回了 `EAGAIN`）

别把现象当原因。

**为什么用 `size()` 而不是 `size() - sent` 判水位**：
`size()` 才是真实内存占用。已发送的部分因为惰性删除还没释放，
内存确实还占着。所以水位看 `size()`。

## 水位线：为什么必须做，为什么选择"踢"

### 不打这个补丁会怎么死

```
客户端网络差 → send 一直 EAGAIN → sendq 一直涨
→ 涨到几十 MB → 进程被 OOM Killer 砍死
```

**一个客户端就能干掉整台服务器。** 这叫**慢消费者（slow consumer）**。

关键认知：

> **TCP 的流量控制只保护"对端不被打爆"，保护不了"你不被自己撑爆"。**
> 因为 `sendq` 是用户态内存，内核管不着。

### 为什么不能降速

> **视频流的数据有保质期。**

| 类型 | 有保质期吗 | 降速的后果 |
|---|---|---|
| 文件下载 / 网盘 | 没有 | 慢慢发，无所谓 |
| 点播 VOD | 基本没有 | 缓冲一下，用户能接受 |
| **直播 / 实时通话** | **有，只有几百毫秒** | **延迟单调累积，永远追不回来** |

按 2MB/s 生产、0.5MB/s 消费：
第 60 秒的帧要延迟 18 秒到达。**降速不会让积压消失，只会让积压变成延迟。**

### 为什么压缩没用

> **压缩解决的是"带宽不够"，解决不了"对端不消化"。**

而且视频流本来就是 H.264/H.265 压过的，二次压缩收益极小、CPU 开销巨大。

### 为什么"踢"不等于"少客户"

**留着**：占 4MB+ 内存、每次 `EPOLLOUT` 都要为他跑一遍 flush、
体验是"卡成 PPT"、100 个这样的客户能拖垮整个进程让其他 999 个陪葬。

**踢掉**：客户端自动重连，从最新关键帧开始，**画面反而恢复正常**。

这叫 **fail fast**：与其让他半死不活地卡着，不如干脆断开让他重来。
**卡着的客户是负资产。**

### 判断标准（一句话）

> **数据有保质期 → 过期就丢，别降速。**
> **数据没保质期 → 降速，慢慢来。**

### 三个资源动作各管什么

| 动作 | 管什么 | 漏了会怎样 |
|---|---|---|
| `EPOLL_CTL_DEL` | epoll 关注列表 | 内核继续为死连接报事件，CPU 空转 |
| `close(fd)` | fd + 内核 socket 对象 | **fd 泄漏**，1024 个用完就 accept 不了 |
| `map1.erase(it)` | 你的户籍册 | **内存泄漏** + fd 复用后查到"僵尸 Conn" |

**顺序**：`DEL`（先捂耳朵）→ `close`（再关门）→ `erase`（最后抹记录）。

### 验收方法（有坑）

`tc netem` 加在 `lo` 上是**双向限速**的，echo 场景测不出来
（服务端自己也只收到 1.25KB/s，压根产生不了积压）。

正确做法：**让客户端只发不读**。

```bash
python3 -c "
import socket, time
s = socket.create_connection(('127.0.0.1', 8888))
s.sendall(b'A' * 8000000)
time.sleep(300)
"
```

## v4：一对多广播（转发服务器）

### 加了什么

v3 是回声：**你发什么，我回给你**。
v4 是转发：**你发什么，我转给除你之外的所有人**。

`queue_send` / `flush_sendq` / 4MB 水位——**一行没改，全部照搬**。

> 这是分层设计的第一次回报：v3 把"怎么可靠地发出去"封装成了两个函数，
> v4 只需要决定"发给谁"，完全不用操心"发不动怎么办"。

### 结构变化：从回声到星型

```
      回声（v3）                     广播（v4）

   A ←→ 服务端                   推流端
                                  ↓ recv
                              [buffer]
                                  ↓ 遍历 map1
                        ┌─────────┼─────────┐
                        ↓         ↓         ↓
                      拉流A     拉流B     拉流C
```

一个推流端进来，N 个拉流端都能看到——这就是最朴素的直播服务器。

### 核心难点：遍历的时候要踢人

v3 的踢人发生在**单个连接自己的事件分支**里，改的是自己那一条记录，安全。

v4 不一样了：收到一份数据，要遍历**整张 map** 转发。而遍历过程中，
某个接收方可能因为 `queue_send` 失败或超水位需要被踢掉——**边遍历边删**。

```cpp
// 错误：边遍历边删
for (auto it = map1.begin(); it != map1.end(); ++it) {
    if (该踢了) map1.erase(it);   // it 已经失效，下一轮 ++it 是未定义行为
}
```

`erase` 之后那个迭代器就是悬空的，`++it` 等于对野指针做运算。
轻则跳过一个元素，重则段错误——而且这种 bug 不一定每次复现。

### 正确做法：两趟，先记账后清理

```cpp
// 第一趟：只遍历、只转发、只记账，一个都不删
std::vector<int> delete1;
for (auto& kv : map1) {
    if (kv.first == fd) continue;                     // 不转给自己

    if (queue_send(kv.second, buffer, bytes) == -1) {
        delete1.push_back(kv.first);                  // 记下，不动手
        continue;
    }
    if (kv.second.sendq.size() > HIGH_WATER_MARK) {
        delete1.push_back(kv.first);                  // 记下，不动手
        continue;
    }
    // 正常转发，挂 OUT
}

// 第二趟：遍历结束，统一清理
for (int k : delete1) {
    epoll_ctl(epoll_fd, EPOLL_CTL_DEL, k, NULL);
    close(k);
    map1.erase(k);
}
```

**为什么第一趟能用 `for (auto& kv : map1)`？**
range-for 底下也是迭代器，但只要**循环体里不删**，迭代器就不会失效。
危险的不是 range-for，是"删"这个动作。

### 存 fd 还是存迭代器

`delete1` 里存的是 `int`（fd），不是 `iterator`。

| 存什么 | 清理时怎么写 | 要注意什么 |
|---|---|---|
| 迭代器 | `map1.erase(it)` | 得记住"erase 只让被删元素的迭代器失效"这条规则；哪天循环里多一个 insert，rehash 全失效 |
| **fd（key）** | `map1.erase(k)` | 什么都不用记，key 是稳定的 |

`unordered_map::erase(it)` 确实只失效 `it` 自己，其他迭代器仍然有效——
**存迭代器也能跑**。但存 fd 不依赖这条规则，读代码的人一眼就懂。

> **能被删除的东西，用 key 记，别用迭代器记。**

### 三个必须跳过的对象

遍历转发时，有三类连接不能碰：

| 跳过谁 | 为什么 | 漏了会怎样 |
|---|---|---|
| **自己**（`kv.first == fd`） | 不给自己回声 | 推流端看到自己刚发的东西，画面套娃 |
| **发送失败**（`queue_send` 返回 -1） | 连接已经坏了 | 给死人挂门铃，还会继续占 map 位置 |
| **超水位**（`sendq.size() > 4MB`） | 慢消费者 | 一个卡的人拖慢整轮广播 |

前两条用 `continue` 跳过并记账，第三条同理——**注意 `continue` 之后不能再 MOD 挂 OUT**，
否则给一个马上要关的 fd 订阅事件。

### 为什么水位检查必须放在广播这里

v3 的水位是"防自己撑爆"。v4 里它变成了**一对多的放大器**：

```
推流端发 1KB
   → 转发给 100 个拉流端 = 100KB 的出流量
   → 其中 1 个拉流端网速慢，sendq 涨
   → 它涨得比谁都快，因为源头一直在喂
```

**收进来是 1 份，发出去是 N 份。** 这就是广播场景下水位比单连接更关键的原因。

### 还能再省一点：OUT 不是每次都该挂

现在的写法是转发完**无条件**挂 `EPOLLOUT`：

```cpp
queue_send(kv.second, buffer, bytes);
pev.events = EPOLLOUT | EPOLLIN | EPOLLET;   // ← 不管发没发完都挂
epoll_ctl(epoll_fd, EPOLL_CTL_MOD, kv.first, &pev);
```

但大多数情况下 `queue_send` 里的 `send` 是一次成功的（`sent == size()`），
**队列是空的，根本不需要订阅可写**。结果：

```
这一轮挂了 OUT
  → 下一轮 epoll_wait 立刻报可写（因为发送池空着）
  → flush_sendq 一看没货
  → MOD 又把 OUT 摘掉
  → 白跑一圈
```

每收到一次数据就白跑一圈 `epoll_wait` + 两次 `epoll_ctl`。单个连接看不出来，
几百个连接同时转发就是可观的空转。

```cpp
// 只有真的还有剩，才值得挂
if (kv.second.sent < kv.second.sendq.size()) {
    pev.events = EPOLLOUT | EPOLLIN | EPOLLET;
    epoll_ctl(epoll_fd, EPOLL_CTL_MOD, kv.first, &pev);
}
```

这正是 v3 那句 `sent < size()` 的第二次应用——**同一个判断，从"该不该挂"变成"该不该留"**。

### 怎么验收

```bash
# 三个终端：1 个推流端 + 2 个拉流端
python3 -c "
import socket, time
s = socket.create_connection(('127.0.0.1', 8888))
for i in range(100):
    s.sendall(f'msg {i}\n'.encode())
    time.sleep(0.1)
"
```

推流端每发一条，两个拉流端都要收到同一条。**推流端自己不应该收到回显。**

踢人验证同 v3：让一个拉流端只连不读，灌到 4MB 看它是否被单独踢掉、另一个是否安然无恙。

## 高频错题本（反复犯的）

按出错模式归类，比按版本记更有用：

### 模式 1：`errno` 三态判断

- `EAGIN` 拼写错
- `EAGAIN | EWOULDBLOCK`（位或，永远真）
- `if (errno = EINTR)`（赋值）
- 把 `recv == 0` 当成功

**口诀**：`>0` 有数据 / `==0` 对端关了 / `-1` 看 errno。
**`errno` 只在失败时有意义。**

### 模式 2：资源清理三件套

- 只 `erase` 不 `close` → CPU 100%
- 顺序反了
- 清理完还用 `it` / `conn`（悬空引用）

**口诀**：**DEL → close → erase**，一步不能少，顺序不能反。

### 模式 3：循环边界（`continue` / `break` 跳哪一层）

- 错误分支里 `continue` 跳回 `while(1)`，对已关闭的 fd 继续 `recv`
- 同样是 `continue`，在 `for` 里跳事件、在 `while` 里跳下一轮 —— **跳的层级不同，一个对一个错**

**口诀**：**踢完人必须立刻 `break`，不能再碰那个 fd。**

### 模式 4：`epoll_ctl(MOD)` 是替换不是追加

- 写成 `EPOLLOUT | EPOLLET`，把 `EPOLLIN` 抹掉了

**口诀**：**挂 OUT 永远是"在原有基础上加一位"。**

### 模式 5：返回值 vs 状态

- 想用 `flush_sendq` 的返回值判断"发完没有"，但它返回 0 有两种含义
  （清空了 / 撞上 EAGAIN 暂停了）
- `queue_send` 返回值丢弃

**口诀**：**返回值回答"出没出错"，状态回答"干完没有"。**
别让一个返回值同时回答两个问题。去问 `Conn` 本身（`sent` / `size()`），
别问二手转述。

### 模式 6：搞错作用对象

- `fcntl(server_fd, ...)` 设到了门上
- `close` 写在 `if` 外面
- 给已死的连接挂门铃

**口诀**：**门是门，人是人。`server_fd` 和 `client_fd` 永远是两回事。**

### 模式 7：C++ 语言细节

- `std::end` vs `std::endl`
- `cout << buffer` vs `cout.write(buffer, n)`
- `printf` 格式符与类型不匹配（`long` 用 `%ld`）
- 带 NSDMI 的结构体在 C++11 下不是聚合体
- `find` 之后必须判 `end()`

**口诀**：**`end()` 是墙，不是空位。不能从墙上抽书。**
