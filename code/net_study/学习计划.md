## P0 · 传输层内功收尾（1.5 天）

**目标**：把"一个线程管 N 个连接 + 数据高效搬运"练到能画图讲清。

### 动手

1. **v4 转发服务器**：v3 的 echo 改成"一个推 → 多个收"
   - 关键改动：`recv` 到的数据不再回给同一个人，而是遍历 `map1` 分发给所有其他连接
   - 每个下游各自有自己的 `sendq` 和 `EPOLLOUT` 状态
   - **会第一次真正撞上 `it == map1.end()`**：A 断开时要顺带清理所有下游
   - 验收：3 个 `nc` 连上，第 1 个发，第 2、3 个都收到

2. **零拷贝改造**：转发路径从 `recv + send` 换成 `splice`
   - `splice(client_fd, NULL, pipefd[1], NULL, len, SPLICE_F_MOVE)`
   - `splice(pipefd[0], NULL, target_fd, NULL, len, SPLICE_F_MOVE)`
   - 验收：`strace -c -f ./v4` 对比改造前后，看 `read`/`write` 是否变成 `splice`，以及时间占比

3. **Nagle 实验**：同一份 100 个小包
   - 分别用默认 / `TCP_NODELAY` / `TCP_CORK` 三种模式发
   - 用 `tcpdump -i lo -w x.pcap` 抓包，数包数量
   - 验收：写清"为什么推流必须关 Nagle，而某些场景用 CORK 更好"

### 面试产出

能讲清：
- LT 和 ET 的本质差异，为什么 ET 必须读到 EAGAIN
- `EPOLLOUT` 为什么必须按需挂、用完摘（常挂 = CPU 空转）
- `sendfile` / `splice` 分别省掉了哪几次拷贝

## P1 · RTP / RTCP（1.5 天）

**目标**：理解"媒体流怎么在 UDP 上传输，质量怎么反馈"。

### 动手

1. **最小 RTP 打包器**
   - 12 字节固定头：`V=2 | P | X | CC | M | PT | seq(16) | timestamp(32) | SSRC(32)`
   - 一帧大于 MTU 时的分片（H.264 用 FU-A，看 NAL 头 + 起始/结束标志）
   - 验收：Wireshark 能正确解析你发的包，`seq` 连续、`timestamp` 按 90kHz 递增

2. **RTCP RR（Receiver Report）**
   - 统计：累计丢包数、丢包率、抖动（jitter）
   - 验收：抓包看到 RR 报文，字段值和你算的对得上

### 关键概念（必须搞懂）

- 时间戳为什么是 90kHz（不是 1kHz）
- 序列号回绕怎么处理（16 位，约 11 分钟就绕一圈）
- SSRC 冲突检测
- RTCP 为什么必须周期发（默认 5 秒），不发会怎样

## P2 · QoS 三件套（2 天）

**目标**：理解弱网下"怎么救画面"，以及三种手段的取舍。

### 动手

1. **NACK（丢包重传）**
   - 接收端：发现 `seq` 有空洞 → 发 NACK 报文
   - 发送端：维护一个**重传缓存**（最近 N 个包），收到 NACK 就重发
   - 验收：`tc netem loss 5%` 下，开 NACK 前后画面差异（花屏 vs 恢复）

2. **FEC（前向纠错）**
   - 先做最简单的**异或 FEC**：k 个数据包 + 1 个校验包
   - 验收：丢 1 个包能恢复，丢 2 个不能——亲眼看这个边界

3. **拥塞控制（只读，不写）**
   - GCC：基于**延迟梯度**判断拥塞（适合实时）
   - BBR：基于**带宽时延积**建模
   - 输出一页笔记：**为什么实时流不能直接用 TCP 的拥塞控制**

### 关键取舍（面试必问）

| 手段 | 适用场景 | 代价 |
|---|---|---|
| NACK | 低延迟、RTT 小、丢包率低 | 增加 RTT 延迟 |
| FEC | 高丢包、RTT 大（来不及重传） | 增加带宽开销 |
| 拥塞控制 | 所有场景都要 | 实现复杂 |

## P3 · RTMP CHUNK 分块（1.5 天）

**目标**：理解"多条消息怎么复用到一条 TCP 上"。

### 动手

1. **握手**：C0/C1/C2 + S0/S1/S2（可以先跳过复杂加密）
2. **Chunk 解析**
   - Chunk 基本头：`format(2) | csid(6)`
   - 四种消息头格式（type 0/1/2/3）分别省略了哪些字段
   - 扩展时间戳（timestamp == 0xFFFFFF 时）
   - 验收：ffmpeg 推流过来，你能打印出收到的消息类型（音频/视频/命令）和长度

3. **解析 `connect` / `publish` 命令**（AMF0 编码，可以先只解析字符串）

### 关键概念

- 为什么 RTMP 用 chunk 而不是直接发消息（复用小包，减少 TCP 开销）
- chunk size 协商
- RTMP 基于 TCP，为什么还会延迟（GOP 缓冲 + TCP 队头阻塞）

## P4 · HLS 切片策略（1 天）

**目标**：理解"为什么 HLS 延迟高但兼容性好"。

### 动手

1. 用 ffmpeg 切 TS 片 + 生成 m3u8，观察切片边界和关键帧对齐
2. **自己写极简 HTTP 服务器分发 m3u8 + ts**（复用 v1 的 epoll 框架）
   - 验收：VLC 打开 `http://localhost:8080/index.m3u8` 能播

### 关键概念

- 切片时长 vs 延迟的取舍（2s 切片 ≈ 6-10s 延迟）
- 为什么必须 GOP 对齐
- TS 封装 vs fMP4 封装
- LL-HLS 的 partial segment 怎么把延迟压到 2s

## P5 · SRT / QUIC（0.5 天，只读）

**目标**：能说清"为什么需要它们"，不写代码。

- **SRT**：基于 UDT，ARQ + AES 加密，主打公网抗丢包
- **QUIC**：0-RTT、流级多路复用（无队头阻塞）、连接迁移

**产出**：一页对比表（TCP / RTMP / SRT / QUIC），按"延迟 / 抗丢包 / 兼容性 / 实现成本"四个维度。

## P6 · 整合 + 云服务器部署（2 天）

1. **串起来**：RTMP 推流 → 解析 → 转 RTP 或 HLS 分发
