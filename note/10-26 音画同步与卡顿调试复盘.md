> 日期：2026-10-26
> 项目：`ffmpeg_study/code/PlayerProject`（FFmpeg + SDL2 直播播放器）
> 用途：明天复习用。建议先看「一、结论」，再按「四、六个根因」逐个过，最后用「五、自测题」检验。

## 一、先说结论

这一整天所有的问题，归结成三句话：

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 时间从哪来 | 用 `m_baseTime` 把流的绝对 pts 归一化；音频钟锚定到**音频帧的 PTS**，不是字节数 |
| 2 | 什么时候消费队列 | **先 peek 看，到点才 pop**。等待期间绝不消费队列 |
| 3 | 什么时候提交画面 | **没画新帧就不 Present**。双缓冲下每次 Present 都是一次翻页 |

数据流的五个环节：

```
读(demux) → 解(decode) → 同步(sync) → 渲染(render) → 提交(present)
```

**五步里任何一步的"时机"错了，用户看到的都是错的。** 今天修的不是逻辑，全是时机。

## 四、六个根因（重点）

### 根因 1：阻塞生产者 → 音频饿死 → 互锁

**现象**：`mediamtx` 日志刷 `reader is too slow, discarding 27 frames`，画面卡顿。

**原来的代码**（`Player::demuxLoop`）：

```cpp
while(m_videoRenderer.queueSize() >= 30 && m_isRunning)
    std::this_thread::sleep_for(std::chrono::milliseconds(5));
```

**为什么错**：

```
视频队列满 → demux 停读 → RTMP socket 不读
   → 服务端判定 slow reader → 丢最老的 GOP
   → 同时音频也被饿死（同一个 demux 线程！）
      → 音频钟不前进 → 视频 delay 巨大 → 消费更慢 → 队列更满
```

**这是消费者把生产者掐死的经典死锁。** 而且那个 `while` 还躺在 `m_seekMutex` 的 lock_guard 里，卡住时连 seek 都进不去。

**修法**：直播流绝不阻塞生产者，满了丢最老的。

```cpp
while(videoframeQueue.size() >= m_maxQueueFrames)
{
    AVFramePtr dropped;
    if(!videoframeQueue.try_pop(dropped)) break;
}
```

### 根因 2：`swr_convert` 的指针层级

**现象**：黑屏然后闪退，无任何报错。

**原来的代码**：

```cpp
swr_convert(swr_ctx.get(), (uint8_t**)m_pcmBuf.data(), output_samples, ...);
```

**为什么错**：

`swr_convert` 的第二个参数是**平面指针数组**，`out[0]` 必须是目标地址。

| 你以为传的 | swr 实际看到的 |
|---|---|
| `m_pcmBuf.data()` = PCM 数据起始地址 | `out` 指向 PCM 数据的**头 8 个字节** |
| `out[0]` = 数据地址 | `out[0]` = **头 8 字节音频数据被当成一个指针** |

swr 拿着这个"由采样值拼出来的假地址"去写音频 → 段错误。

**正确写法**：

```cpp
uint8_t* out_planes[1] = { m_pcmBuf.data() };
swr_convert(swr_ctx.get(), out_planes, output_samples, audio_frame->data, nb_samples);
```

**对比三个版本**：

```cpp
swr_convert(ctx, (uint8_t**)m_pcmBuf.data(), ...)   // ✗ 数据地址当指针数组
swr_convert(ctx, (uint8_t**)&m_pcmBuf[0], ...)      // ✗ 同上
uint8_t* out_planes[1] = { m_pcmBuf.data() };
swr_convert(ctx, out_planes, ...)                    // ✓ 真正的指针数组
```

> 补充：`audio_frame->data` 能直接传，因为 `AVFrame::data` 本身就是 `uint8_t*[8]`，天然是指针数组。

### 根因 3：音频回调必须"填满"

**现象**：周期性"咔哒"声 + 渐进失步。

**原来的代码**：一次回调只取一帧，不够补静音、多了丢样本。

```cpp
int copy_len = min(convertbytes, len);
SDL_memcpy(stream, out_buffer[0], copy_len);
if(copy_len < len) SDL_memset(stream + copy_len, 0, len - copy_len);   // 补静音
```

**为什么错**：SDL 音频回调是硬实时的，必须在当前 buffer 播完前填满。而"一帧 ≈ 一个 len"这个假设在 VFR 源、重采样、seek 后都不成立。

- 大了 → 丢样本 → 音频内容比时钟跑得快 → 越播越偏
- 小了 → 补静音 → 波形被硬切 → 一声"咔"

**正确模型**：PCM 是一条连续的字节流，回调只负责从里面取够 `len` 字节。

```cpp
while(written < len)
{
    if(m_pcmPos >= m_pcmBuf.size())      // 当前帧用完，取下一帧
    {
        if(!audioframeQueue.try_pop(audio_frame)) break;   // 真没粮了，剩下留静音
        // swr 转换到 m_pcmBuf，重置 m_pcmPos
    }
    int copy = min(m_pcmBuf.size() - m_pcmPos, len - written);
    SDL_memcpy(stream + written, m_pcmBuf.data() + m_pcmPos, copy);
    written += copy;
    m_pcmPos += copy;
    m_frameBytes += copy;        // ← 必须在循环内
}
```

**别忘了**：回调里还要挡掉 `swr_ctx` 为空、`output_samples <= 0`、`output_size <= 0`。**回调函数里绝不能让异常逃出去**，它跑在别人的线程里，一个异常就是整个进程的死讯。

### 根因 4：字节钟 vs PTS 钟

**现象**：`delay` 恒为 +2.1 秒，每秒只画 1 帧。

**原来的代码**：

```cpp
m_playerbyte += len;
audio_clock = m_playerbyte / m_bytepersecond;
```

**为什么错**：这个钟数的是"喂给声卡多少字节"，**它不知道队列里丢过帧**。

```
音频队列上限 60 帧 → 启动突发时丢掉 100 帧
  → 音频内容已经跳到 2.3 秒处
  → 但字节钟还停在 0.51 秒（设备只播了这么多量）
  → 视频 pts 是真实的流时间 2.35 秒
  → delay = 2.35 - 0.51 = +1.84 → 干等
```

**正确做法**：锚定到音频帧的 PTS（ffplay 的思路）。

```cpp
// 取到新帧时
m_framePts = audio_frame->pts * av_q2d(m_audioTimeBase) - m_baseTime;
m_frameBytes = 0;

// 回调末尾
audio_clock = m_framePts + (double)m_frameBytes / m_bytepersecond
                         - (double)len / m_bytepersecond;
```

减 `len/byteps` 是补偿 SDL 的内部缓冲延迟（一个 period ≈ 23ms）。

**关键区别**：

| | 字节钟 | PTS 钟 |
|---|---|---|
| 数的东西 | 喂了多少数据 | 现在播的是流里第几秒 |
| 丢帧后 | 不知道，继续按原节奏走 | 立刻跟到新位置 |
| 适用 | 不丢帧的点播 | 会丢帧的直播 |

### 根因 5：先取再等 → 先看后取

**现象**：`q` 恒满、`画=1`、`rawpts` 每 1~2 秒才跳一次。

**原来的代码**：

```cpp
if(!m_pendingFrame)
{
    if(!videoframeQueue.try_pop(m_pendingFrame)) return;   // 先取出来
}
// ... 算 delay ...
if(delay > 0.005) return;      // 太早，攥着这帧等
```

**为什么错**：等待期间生产者还在灌队列，满了就丢——**丢掉的正是接下来该播的帧**。

需要的队列深度 ≈ `delay × fps`，而 delay 又受队列影响 → **正反馈，调数字永远追不上**。

| 帧率 | delay | 需要 | 上限 48 |
|---|---|---|---|
| 28.6 | 0.69 | 20 帧 | ✅ |
| 60 | 0.5~1.0 | 30~60 帧 | ❌ |

**正确做法**：先 peek 看队首的 pts，不到点就 return，**队列一个字节都不动**。

```cpp
int64_t frontPts = AV_NOPTS_VALUE;
if(!videoframeQueue.peek([&](AVFramePtr& f){ frontPts = f->pts; }))
    return;

double pts_sec = (frontPts != AV_NOPTS_VALUE)
               ? frontPts * av_q2d(m_timebase) - m_baseTime : 0.0;
// ... 算 delay ...

if(delay > 0.005) return;                              // 没到点，队列不动
if(!videoframeQueue.try_pop(m_pendingFrame)) return;   // 到点才取
if(delay < -0.15) { m_pendingFrame.reset(); return; }  // 过期太久，丢掉
```

**`peek` 的实现要点**（`ThreadSafeQueue.h`）：

```cpp
template <typename Fn>
bool peek(Fn&& fn)
{
    std::lock_guard<std::mutex> lock(mtx);
    if(data_queue.empty() || m_isstoped) return false;
    fn(data_queue.front());
    return true;
}
```

> 为什么用回调而不是返回 `T&`：函数一返回锁就释放了，返回的引用指向队列内部，下一秒可能被 pop 掉 → use-after-free。**锁的作用范围要覆盖"你操作数据的时间范围"。**

### 根因 6：Present 双缓冲翻页

**现象**：画面在两帧之间来回跳，看起来像"回退"。

**原来的代码**（`main.cpp`）：

```cpp
player.renderVideoFrame();
progressBar.draw(...);
SDL_RenderPresent(...);        // 每 1ms 一次，每秒 450~1000 次
sleep(1ms);
```

**为什么错**：SDL 是双缓冲，每次 `Present` 是一次缓冲交换。

```
画第 N 帧 → Present → 显示 N
没画新帧 → Present → 显示 N-1   ← 旧画面
没画新帧 → Present → 显示 N     ← 又翻回来
```

**它永远在 N 和 N-1 之间来回跳。** 视觉上的严重程度取决于两帧隔多久：

| 场景 | 帧间隔 | 观感 |
|---|---|---|
| 30fps | 33ms | 看不出来 |
| 60fps | 17ms | 更看不出来 |
| 1fps（修复前） | 1000ms | **明显"回退"** |

**同一个 bug，被帧率放大。** 这就是为什么本地文件从来没暴露、直播一上来就炸。

**修法**：脏标记 + 条件提交。

```cpp
// VideoRenderer.h
bool takeFrameDrawn(){ return m_frameDrawn.exchange(false); }
private:
std::atomic<bool> m_frameDrawn{false};

// renderOneFrame 末尾
m_frameDrawn = true;

// main.cpp
if(player.takeFrameDrawn())
{
    progressBar.draw(player.getRenderer());
    SDL_RenderPresent(player.getRenderer());
}
```

`exchange(false)` = 读走并清零，**一次标记对应一次 Present**。

## 五、核心概念（自测题）

### Q1：为什么音频是主时钟，视频不是？

**因为音频不能改，视频可以改。**

- SDL 声卡按 44100Hz **硬性**消耗数据，你填什么它播什么，快不了也慢不了（除非改采样率，那会变调）
- 视频是一串离散图片，你可以选择现在画哪张、跳不跳帧

所以"主时钟"的意思是：**以谁的时间进度为准**。选音频，是因为它没有自由度。

**音频没有"跟着时钟走"这个动作——音频就是那个钟本身。**

### Q2：队列上限 48 帧意味着什么？

**它本身没有意义，必须结合"满了会怎样"才有意义。**

| 策略 | 队列深度的含义 | 决定什么 |
|---|---|---|
| 背压（满了等） | 缓冲时间 | 抗抖动能力，代价是延迟 |
| 丢最老（满了丢） | 每轮销毁量 | 画面完整性 |

而且：**帧数 × 帧间隔 = 时间**。

| 队列上限 | 24fps | 30fps | 60fps |
|---|---|---|---|
| 48 帧 | 2.0 秒 | 1.6 秒 | **0.8 秒** |

分辨率**只影响内存**，不影响缓冲时间。1080p 换 4K，48 帧还是 48 帧，只是内存从 150MB 涨到 600MB。

**所以队列深度应该按时间算：**

```cpp
AVRational fr = av_guess_frame_rate(...);
double fps = av_q2d(fr);
std::size_t cap = (std::size_t)(fps * 2.0);    // 2 秒
```

### Q3：队列深度会影响到音画同步吗？

**不会。** 同步只由时钟决定。

音频队列深 → demux 提前读更多 → 这些音频排队等着播 → 音频钟跟着正在播的那一帧走 → 视频跟着钟走。

无论队列是 60 帧还是 600 帧：**音画永远同步，变化的只是端到端延迟**。

**延迟 ≠ 不同步。**

### Q4：为什么归一化时音视频必须共用一个 base？

假设音频从 0.000s 开始、视频从 0.040s 开始（很常见，视频要等关键帧）：

```
正确（共用 base=0.000）：
  视频 rel = 0.040 - 0.000 = 0.040
  音频 origin = 0.000 - 0.000 = 0.000
  → 差 40ms，保留了真实偏移 ✓

错误（各自减自己的首帧）：
  视频 rel = 0.040 - 0.040 = 0.000
  音频 origin = 0.000 - 0.000 = 0.000
  → 差 0，真实偏移被抹掉 ✗
```

**归一化的目的不是"让每个流都从 0 开始"，而是"让时间轴对齐到你加入的那一刻"。**

### Q5：为什么 `m_baseInited` 要单独一个 bool？

因为 `m_baseTime` **完全可能合法地等于 0**（从 0 开始的点播文件）。

```cpp
if(m_baseTime == 0.0)    // ✗ 分不清"没算过"和"算出来就是0"
```

**用值来判断状态，是最常见的坑之一。状态就该有独立的状态位。**

### Q6：`m_playerbyte` 为什么不能是负数？

它是 `uint64_t`。`(uint64_t)(-0.08 * 176400)` 不会得到 `-14112`，而是：

```
18446744073709551616 - 14112 ≈ 1.8 × 10¹⁹
```

除以 `bytepersecond` → 时钟变成一亿亿秒 → 视频每帧都被判"过期" → 黑屏。

**无符号数不会"变成负数"，它会绕回成天文数字。** 所以时钟原点用独立的 `double` 装，可以合法为负。

## 七、调试方法论

### 7.1 探针（最有价值的工具）

在 `renderOneFrame` 里每秒汇总一次：

```cpp
printf("[1s] 画=%d 丢=%d 等=%d 空=%d 推=%d 推丢=%d 取=%d q=%zu | rawpts=%lld rel=%.3f clock=%.3f delay=%.3f\n", ...);
```

| 字段 | 正常 | 异常说明什么 |
|---|---|---|
| 画 | ≈ fps | 远小于 fps → 渲染跟不上 |
| 丢 | ≈0 | 几百 → 时钟跑太快，在狂追 |
| 等 | 几百（主循环 1ms 一轮） | 接近 1000 且 画≈0 → 时钟停住或滞后 |
| 空 | 几十 | 接近 1000 → 队列长期空，帧没送到 |
| 推 | ≈ fps | 远小于 fps → 推流端掉帧 |
| 推丢 | **0** | 不为 0 → 队列上限在杀帧 |
| 取 | ≈ 画+丢 | 远小于 推 → 消费端被卡住 |
| q | 稳定在中段 | 常年顶死 → 缓冲不够 |
| rawpts | 单调递增 | 忽大忽小 → **PTS 真的在回退** |
| rel / clock | 两者接近 | 差距持续拉大 → 基准错位 |
| delay | ±0.05 | 恒定 ±1 以上 → 时钟源有问题 |

### 7.2 三个真实的误判

| 误判 | 真相 | 教训 |
|---|---|---|
| 用 1fps 抽帧看录屏，以为"能跑" | 闪烁和回退是高频现象，1fps 完全看不到 | **采样率低于现象频率，等于没测** |
| 像素比对发现"A→B→A"就判定为回退 | 那是过场动画的镜头对切 | 图像相似度不等于播放正确 |
| 相信"9 条 bug 清单"里的每一条 | 其中 3 条是错的，照改会更糟 | **别人的分析可以当线索，不能当结论** |

### 7.3 排查顺序

```
画面不对
```

### 参数含义

| 参数 | 作用 | 不加会怎样 |
|---|---|---|
| `-re` | 按原始帧率读 | 全速推完，播放器来不及接 |
| `-stream_loop -1` | 无限循环 | 播到结尾 demux 退出，画面冻住 |
| `-tune zerolatency` | 关 B 帧、关前瞻 | 编码器攒帧，延迟涨几百毫秒 |
| `-g 30` | 每 30 帧一个关键帧 | GOP 太长，启动慢、seek 卡 |
| `-preset ultrafast` | 最快编码 | 虚拟机可能压不动 |
